**V2.0, erste Release des Epics.** Danach ist HomeFlow fachlich eine
Haustier-App: es gibt keine Ausgabe, keinen Termin und keinen Einkaufsartikel
mehr ohne Tierbezug.

## Ausgangslage, gemessen am 2026-09-01

    Ausgaben 2 (davon 1 ohne Tier) · Kalendereinträge 0 · Einkaufsartikel 0
    Belege 0 · Tiere 1 · Benutzer 2

**Die Datenmigration kostet real eine Zeile.** Der Zuordnungsschritt unten
gehört trotzdem gebaut — er ist die Vorlage für jeden späteren NOT-NULL-Umbau
und wäre bei gefüllter Datenbank die halbe Arbeit.

## Migration `000021_pet_scope` (reserviert in contracts.md 1.3)

    -- up
    -- 1. Zuordnung vor Constraint: verwaiste Zeilen sichtbar machen, nicht raten.
    --    Kein Default, kein "nimm das erste Tier". Wer keine Zuordnung hat,
    --    bekommt sie von einem Menschen oder die Migration bricht ab.
    DO $$ DECLARE n int; BEGIN
      SELECT count(*) INTO n FROM expenses WHERE pet_id IS NULL;
      IF n > 0 THEN RAISE EXCEPTION
        'HF-0116: % Ausgabe(n) ohne Tier. Vor der Migration über die API zuordnen '
        'oder löschen; die Migration erfindet kein Tier.', n;
      END IF;
    END $$;
    -- dasselbe für calendar_events

    ALTER TABLE expenses        ALTER COLUMN pet_id SET NOT NULL;
    ALTER TABLE calendar_events ALTER COLUMN pet_id SET NOT NULL;

    -- 2. Die generische gemeinsame Liste verschwindet.
    DELETE FROM shopping_lists WHERE id = '00000000-0000-4000-8000-000000000100';

    -- down
    ALTER TABLE expenses        ALTER COLUMN pet_id DROP NOT NULL;
    ALTER TABLE calendar_events ALTER COLUMN pet_id DROP NOT NULL;
    INSERT INTO shopping_lists (...) -- Standardliste wiederherstellen

`households` und `household_members` bleiben **unverändert**. Sie sind die
Mandantengrenze, an der die Zwei-Benutzer-Regel (Migration 000002) und jede
Autorisierungsabfrage hängen. Wer sie anfasst, fasst das ganze Schema an, ohne
dass das Produkt davon etwas hat.

## Code

- `backend/internal/expenses/model.go`: `PetID *string` → `PetID string`.
  Der Zeiger ist die einzige Stelle, an der "ohne Tier" heute überhaupt
  darstellbar ist; solange er bleibt, kommt der Zustand zurück.
- `backend/internal/calendar/model.go`: dito.
- `backend/internal/shopping/`: `SharedListID` und der `"shared"`-Fallback in
  `service.go` (drei Stellen: Zeilen um 41, 73, 105) entfallen. Ein Artikel
  gehört zu einem, mehreren oder allen Tieren — über `shopping_item_pets`.
  "Alle Tiere" ist **keine** leere Menge, sondern eine ausdrückliche Markierung,
  sonst ist es von "vergessen" nicht unterscheidbar.
- Validierung: fehlender Tierbezug ist ein 400 mit einer Meldung, die sagt was
  fehlt — nicht ein 500 aus dem Constraint.

## API

`POST/PATCH /api/v1/expenses` und `/api/v1/calendar` verlangen `petId`.
`docs/api/openapi.yaml` im selben Durchgang, sonst ist die Spezifikation falsch,
und seit HF-0099 fällt das auf.

## Migration 000021

Zuordnung vor Constraint, wie im Ticket beschrieben. Die Gegenprobe ist der
eigentliche Nachweis: mit einer künstlich eingefügten Ausgabe ohne Tier meldet
die Migration

    ERROR: HF-0116: 1 Ausgabe(n) ohne Tierbezug. Vor der Migration über
           PATCH /api/v1/expenses/{id} einem Tier zuordnen oder löschen.
           Die Migration errät kein Tier.

und danach ist **nichts halb migriert** — `pet_id` bleibt in beiden Tabellen
nullbar. Das liegt nicht am Zufall: `postgres.Migrate` fasst jede Datei ohnehin
in eine eigene Transaktion, was ich nachgelesen und im Migrationskopf vermerkt
habe, damit niemand ein zweites BEGIN hineinschreibt.

`.down.sql` einmal ausgeführt und der Vorzustand wiederhergestellt.

## Code

Der Zeiger fällt: `PetID *string` → `PetID string` in `Expense`,
`CreateExpense`, `Event` und `EventInput`. Der Zeiger war die einzige Stelle,
an der „ohne Tier" überhaupt darstellbar war — solange er bleibt, kommt der
Zustand über irgendeinen Aufrufer zurück.

Der Compiler hat 17 Folgestellen benannt. Ich habe jede einzeln angesehen statt
sie zu ersetzen; an einer Stelle hatte ich zwischendurch ein `if false { … }`
stehen lassen, das ist raus.

## Zwei Abweichungen vom Ticket

**Die gemeinsame Liste wird umbenannt, nicht gelöscht.** Das Ticket sagte
„verschwindet", und fachlich stimmt das. Technisch hängen aber alle Artikel per
Fremdschlüssel an `shopping_lists`; ein `DELETE` hätte jeden vorhandenen Artikel
mitgenommen. Was verschwindet, ist der Artikel ohne Tierbezug, nicht der
Behälter. Sie heißt jetzt „Tier-Einkaufsliste".

**Der geplante CHECK entfällt.** „Mindestens ein Tier oder `for_all_pets`"
hängt an `shopping_item_pets`, und eine Zeilenprüfung liest keine zweite
Tabelle. Ein Trigger wäre möglich und auf einem Zwei-Personen-System mehr
Maschinerie als Nutzen. Durchgesetzt wird es im Dienst; die Migration sagt an
der Stelle ausdrücklich, dass das Schema hier nicht hilft. Gegengeprüft: nimmt
man die Prüfung aus dem Dienst, fällt `TestItemWithoutAnyPetScopeIsRejected`.

Im Ticket stand ursprünglich ein `CHECK (for_all_pets OR true)` — der ist immer
wahr und prüft nichts. Mein Fehler beim Schreiben des Tickets.

## Tests

Die Kalender- und Ausgabenfixtures prüfen jetzt am Tier statt an „Müllabfuhr"
und „Groceries". Das waren Haushaltstermine, die es fachlich nicht mehr gibt;
geprüft wird weiterhin dasselbe — Sichtbarkeit, Wiederholung, Erinnerung,
Beleg-Isolation. Neu sind Fälle für „Ausgabe ohne Tier" und „Artikel ohne
jeden Tierbezug".

## Nicht geprüft

  gewollt, aber du sollst es vorher wissen und nicht am roten Deploy merken.
