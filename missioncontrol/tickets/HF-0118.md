**V2.1, das Herzstück des Epics.** Heute ist ein Tierarztbesuch bis zu acht
unverbundene Zeilen: Diagnose, Behandlung, Impfung, Medikament, Laborwert,
Gewicht, Dokument, Ausgabe. Der Besuch selbst existiert nicht.

## Migration `000023_medical_encounters`

    CREATE TABLE medical_encounters (
      id             uuid PRIMARY KEY,
      household_id   uuid NOT NULL REFERENCES households(id) ON DELETE CASCADE,
      pet_id         uuid NOT NULL,
      veterinarian_id uuid,
      occurred_on    date NOT NULL,
      practice_text  text NOT NULL DEFAULT '' CHECK (length(practice_text) <= 200),
      title          text NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
      summary        text NOT NULL DEFAULT '' CHECK (length(summary) <= 4000),
      status         text NOT NULL DEFAULT 'offen'
                     CHECK (status IN ('offen','abgeschlossen')),
      created_by     uuid NOT NULL REFERENCES users(id),
      created_at     timestamptz NOT NULL DEFAULT now(),
      updated_at     timestamptz NOT NULL DEFAULT now(),

      FOREIGN KEY (household_id, veterinarian_id)
        REFERENCES veterinarians(household_id, id) ON DELETE SET NULL,
      UNIQUE (household_id, id)
    );
    CREATE INDEX medical_encounters_timeline_idx
      ON medical_encounters(household_id, pet_id, occurred_on DESC, id DESC);

    -- Die Klammer. Polymorph, weil sonst neun Verknüpfungstabellen entstehen,
    -- die alle dasselbe tun.
    CREATE TABLE encounter_items (
      household_id uuid NOT NULL,
      encounter_id uuid NOT NULL,
      item_kind    text NOT NULL CHECK (item_kind IN
        ('medical_record','vaccination','pet_medication','lab_report',
         'weight_entry','document','expense','insurance_claim','appointment')),
      item_id      uuid NOT NULL,
      created_at   timestamptz NOT NULL DEFAULT now(),
      PRIMARY KEY (household_id, encounter_id, item_kind, item_id),
      FOREIGN KEY (household_id, encounter_id)
        REFERENCES medical_encounters(household_id, id) ON DELETE CASCADE
    );
    CREATE INDEX encounter_items_reverse_idx
      ON encounter_items(household_id, item_kind, item_id);

**Der Primärschlüssel ist die Idempotenz.** Ein Ereignis, das zweimal zugestellt
wird, hängt denselben Datensatz nicht zweimal an — das ist genau die Zusage aus
`docs/product/workflows/receipt-to-medical-record.md`, und sie gehört ins
Schema, nicht in eine Prüfung im Code.

Kein Fremdschlüssel auf `item_id`: polymorph geht das nicht. Deshalb prüft der
Service beim Anhängen, dass das Ziel existiert und demselben Haushalt **und
demselben Tier** gehört. Der Test dafür ist Pflicht, weil das Schema hier nicht
hilft.

## Encounter ist optional

Ein Gewicht auf dem Sofa hat keinen Besuch. Pflicht zu machen hieße, jede
Schnellaktion in ein Formular zu verwandeln — genau das, was dieses Epic
beseitigen soll. `medical_records` bekommt deshalb ein **nullbares**
`encounter_id`, kein NOT NULL.

## Service

    encounters.Create(ctx, user, NewEncounter) (Encounter, error)
    encounters.FindOrCreate(ctx, user, pet, vet, date) (Encounter, bool, error)
    encounters.Attach(ctx, user, encounterID, kind, itemID) error
    encounters.Detach(ctx, user, encounterID, kind, itemID) error
    encounters.Get(ctx, user, id) (EncounterDetail, error)

`FindOrCreate` ist der Einstieg für die Belegverarbeitung: sucht über
`(pet, veterinarian, occurred_on)`, legt nur an, wenn nichts passt, und meldet
über das `bool` welcher Fall eintrat. Zwei Besuche am selben Tag in derselben
Praxis kann sie nicht auseinanderhalten — dann liefert sie beide und der
Aufrufer fragt den Benutzer. Nicht raten.

    PATCH  /api/v1/medical-encounters/{id}
    DELETE /api/v1/medical-encounters/{id}
    POST   /api/v1/medical-encounters/{id}/items     { art, id }
    DELETE /api/v1/medical-encounters/{id}/items/{kind}/{itemId}

Löschen eines Encounters löscht **nur die Klammer**, nicht den Inhalt. Ein
Besuch, der falsch angelegt war, darf keine Diagnose mit in den Abgrund nehmen.
Das gehört als Test abgesichert.
