**V2.3.** `event_outbox` existiert seit Migration 000001 und **hat keinen
Schreiber** — das steht als bekannte Falle in AGENTS.md. Jeder Ablauf in
`docs/product/workflows/` setzt sie voraus. Ohne dieses Ticket schreibt man die
Kopplung in V2.4, V2.6 und V2.7 dreimal, jedes Mal anders.

## Schreiben

Ein Ereignis wird **in derselben Transaktion** geschrieben wie die
Zustandsänderung, die es auslöst. Nicht danach, nicht in einer Goroutine.

    outbox.Append(ctx, tx, Event{
      Kind: "medical_encounter.created",
      HouseholdID: ..., AggregateKind: "medical_encounter", AggregateID: ...,
      Payload: minimal, versioniert,
    })

`tx` ist Pflicht im Aufruf. Eine Variante ohne Transaktion gibt es nicht — sonst
nimmt sie jemand, und dann gibt es Ereignisse zu Zuständen, die zurückgerollt
wurden.

**Payload minimal und versioniert.** IDs und der Anlass, sonst nichts: keine
Beträge, keine Diagnosen, keine Dokumentinhalte, keine Secrets. Ein Verbraucher,
der mehr braucht, liest nach. `docs/security/threat-model.md` verlangt das, und
ein Ereignisstrom ist genau die Stelle, an der solche Daten unbemerkt
weiterwandern.

Ereignisse aus `pet-domain-v2.md`: `document.uploaded`, `ocr.completed`,
`ocr.failed`, `document.confirmed`, `medical_encounter.created`,
`vaccination.recorded`, `vaccination.due`, `medication.stock.low`,
`appointment.upcoming`, `expense.created`, `budget.threshold.reached`,
`insurance_claim.created`, `insurance_claim.reimbursed`,
`shopping_item.completed`.

## Zustellen

Ein Dispatcher **innerhalb der API**, kein Broker, kein Kafka.

    SELECT ... FROM event_outbox
     WHERE delivered_at IS NULL AND available_at <= now()
     ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 20

`SKIP LOCKED`, weil sonst zwei Zusteller einander blockieren. Bei Fehlschlag
Versuchszähler hoch und `available_at` exponentiell nach hinten; nach fünf
Versuchen in einen toten Zustand mit sichtbarem Grund — **nicht** stumm
liegenbleiben.

## Idempotenz gehört ins Schema, nicht in den Code

Migration `000025_outbox_idempotency`:

    -- Ein bestätigtes Dokument erzeugt höchstens eine Ausgabe, einen
    -- Encounter, einen Versicherungsfall. Egal wie oft das Ereignis kommt.
    CREATE TABLE workflow_effects (
      household_id uuid NOT NULL,
      source_kind  text NOT NULL,     -- 'document', 'vaccination', 'pet_medication'
      source_id    uuid NOT NULL,
      target_kind  text NOT NULL,     -- 'expense', 'medical_encounter', ...
      target_id    uuid NOT NULL,
      created_at   timestamptz NOT NULL DEFAULT now(),
      PRIMARY KEY (household_id, source_kind, source_id, target_kind)
    );

Der Primärschlüssel **ohne** `target_id` ist die eigentliche Zusage: pro Quelle
und Zielart genau eine Wirkung. Ein zweiter Versuch läuft in einen
Schlüsselkonflikt und liefert die vorhandene ID zurück, statt etwas Neues
anzulegen.

Dazu Indizes auf `event_outbox(delivered_at, available_at)` und die Spalten
`attempts`, `available_at`, `last_error`, falls sie fehlen.

## Beobachtbarkeit

Metriken nach dem bestehenden Muster in `backend/internal/observability/`:
`homeflow_outbox_pending`, `homeflow_outbox_delivered_total{event}`,
`homeflow_outbox_dead_total`. **Metriknamen sind ein Vertrag**
(`contracts.md` 1) — eine Umbenennung leert ein Panel und deaktiviert einen
Alarm, ohne dass etwas fehlschlägt.

Ein Alarm `HomeflowOutboxStalled` auf `homeflow_outbox_pending > 0` für 15
Minuten gehört dazu, sonst merkt niemand, dass der Dispatcher steht.

## Abnahme

- `make ci`, `make integration-test`;
- Test: ein Rollback der Transaktion lässt **kein** Ereignis zurück;
- Test: dasselbe Ereignis zweimal zugestellt erzeugt eine Wirkung, nicht zwei;
- Test: fünf Fehlschläge führen in den toten Zustand mit Grund;
- Test: zwei gleichzeitige Dispatcher greifen sich nicht dieselbe Zeile;
- Test: kein Payload enthält Beträge, Diagnosen oder Dateinamen;
- `contracts.md` 1 (Metriknamen) nachgezogen.
